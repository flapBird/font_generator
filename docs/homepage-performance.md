# 首页延迟与 RSC 预取排查

## 2026-10-25 的线上证据

用户截图中，首页文档约 22 秒，多个带 `_rsc` 查询参数的请求显示红色，
请求头包含 `Next-Router-Prefetch: 1`。这些是 Next.js 页面预取，不能仅凭红色
或 Provisional headers 推断为登录、字体生成接口的 500 错误。

对排查时最近一小时的 Cloudflare 日志进行只读采样并按请求去重：

| 请求 | 样本数 | 返回状态 | Worker 处理耗时中位数 / 最大值 |
| --- | ---: | --- | --- |
| 首页文档 | 24 | 全部 200 | 45ms / 214ms |
| 带 `_rsc` 的页面请求 | 239 | 全部 200 | 22ms / 1575ms |
| 登录会话 | 21 | 全部 200 | 402ms / 2339ms |

这些是采样中的服务端耗时，不能替代浏览器 DNS、连接、TLS、排队及下载时间，
也不能证明被客户端取消或尚未到达 Worker 的请求已成功。
只读获取首页时命中 `x-opennext-cache: HIT`；经过本地代理的首字节约 0.99～1.06 秒，
完整 HTML 约 1.57～2.08 秒。相同机器直连在 TLS 握手阶段超时。
因此未将截图中的 22 秒归因于服务端渲染，也未声称代码修改消除了网络链路延迟。
本次未获取用户浏览器的 Performance trace，未测得可作为线上结论的 LCP 或 INP。

## 可确认的代码优化

首页工具目录、公共导航和页脚包含大量 Next.js Link。原先进入可见区域即预取，
在本地生产构建、1440×1000 视口、阻断外部服务的测量中，首次停留产生 46 次预取，
滚动到页脚后累计 57 次，涉及 40 个目标页面，并出现 7 条失败的 RSC 请求。
在第二次相同场景中，已收到响应的 57 条 RSC 均为 200，7 条失败的错误类型均为
`net::ERR_ABORTED`，复现了浏览器主动取消预取的情况。
这项计数是固定场景的开发测量，不能当作所有设备的请求量。

`components/IntentLink.tsx` 默认关闭可见区域自动预取，在鼠标悬停或键盘聚焦后
恢复 Next.js 自身的预取和缓存机制。首页正文、工具目录、公共导航、账号菜单与页脚
使用此组件。保留真实链接、客户端导航、原有点击处理和显式 prefetch 配置。
登录会话请求仍独立运行，首页文档不等待账户、数据库或字体生成服务。

参考 [Next.js 预取控制文档](https://nextjs.org/docs/app/guides/prefetching)。
此优化不改变公开功能、路由、登录要求、积分或数据处理方式；需检查生成的
`/llms.txt` 仍与实现一致，无需增加性能承诺。

## 验证与后续定位

本地生产浏览器回归检查首页停留和滚动时不触发闲置预取，鼠标悬停／键盘聚焦可预取
目标页面，随后跳转正常。修复后的停留／滚动场景预取数量为 0；用户表达访问意图后
仍会产生正常的目标预取，不承诺整个会话没有 RSC 请求。
测试阻断所有外部 HTTPS 请求，不发送真实 GA4、支付、邮件
或付费审核／生成调用。Workers HTTP 回归另行检查 RSC 树、页面分段与客户端导航。

修复部署后，如果首页文档仍需二十多秒，打开该文档请求的 Timing，比较排队、
连接／SSL、Waiting for server response 和 Content Download，并对比同一时段 Worker
日志。可在相同设备切换代理节点或直连比较，避免仅凭 Network 的 Finish 总时长
判断首页接口耗时；Finish 还包含广告和统计等后续请求。
